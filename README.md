# Interplanetary Survival Guide: Martian Map

A route planner for a Marswalk in Jezero Crater. It answers one question: given a terrain model, which of several walking routes between two points is shortest, fastest, lower risk, or passes the most science targets, and what would it cost in time, climbing, modeled radiation and consumables?

Built for the NASA Space Apps Challenge. It is an educational prototype, not flight software, and is not endorsed by NASA.

## Read this first: what is real and what is not

| Quantity | Status |
|---|---|
| Elevation, slope, distance, climb, route geometry | **Calculated** from whatever terrain model is loaded, using its real pixel spacing in metres |
| Terrain bundled in this repository | **Synthetic test terrain, not Mars** (`public/data/test-terrain.json`) |
| Real Jezero terrain | **Supported, not bundled.** You must supply the NASA HiRISE DTM (see below) |
| Radiation layer | **Modeled.** A reference rate measured by Curiosity at Gale Crater, scaled by terrain horizon blocking |
| Temperature, pressure, dust opacity | **Scenarios you choose.** Not fitted to Perseverance MEDA data |
| Walking speed, endurance, reserve rules | **Assumptions**, listed in the app and below |
| Science targets | Only those supplied inside a tile. The bundled ones are fictional |
| Mineralogy (CRISM), MEDA weather, MOLA, THEMIS, GRS | **Not integrated.** The original interface listed them without using them; they were removed |

Nothing here is a live observation. A GO result is arithmetic on assumed numbers and says nothing about real astronaut safety.

## What works now

- Terrain model with explicit footprint, pixel spacing (m), elevation units (m) and no-data handling.
- Slope from elevation differences divided by the actual horizontal distance (Horn-style, one-sided at borders and next to holes).
- Four route objectives on an 8-connected grid: shortest (3-D length), fastest (slope-dependent walking time), lower risk (slope plus modeled radiation exposure), science (fastest cost reduced near targets).
- Cells above a configurable slope limit (default 25°) or without data are prohibited. If no valid path exists the app says so; it never draws a one-point route.
- Distance, time, ascent, descent, net elevation change, steepest step and modeled dose for each route, plus an elevation profile and warnings with their reasoning.
- Survival check with visible arithmetic and editable assumptions.
- Scale bar, north arrow, coordinate readout (with latitude and longitude when the terrain is georeferenced), legends with units, keyboard control, responsive layout.

## Run it

Needs Node 20+ for tests and Python 3 for tools. The app itself is static files served by Rails (or any static host).

```
npm test                 # unit tests (Node, no dependencies)
python3 test/ui_test.py  # browser tests (needs: pip install playwright && playwright install chromium)
python3 tools/build_dist.py   # rebuild dist/ from the Rails view and public/
```

Rails (Ruby 3.3):

```
bundle install
bin/rails server         # http://localhost:3000
bin/rails static:export  # same output as tools/build_dist.py
```

Static host (Vercel): `vercel.json` serves `dist/`. Docker: `docker build -t mars-survival . && docker run -p 3000:3000 mars-survival`.

## Using the demonstration terrain

It loads automatically. **Terrain model and data sources → Load bundled synthetic test terrain** reloads it. It is a 2.5 × 2.0 km analytic surface (25 m cells) with a gentle tilt, a hill, a 15° mound, a 150 m ridge with one 450 m pass, a no-data patch and three fictional targets. It is generated by `tools/make_test_dem.py`, so judges can reproduce it. Its landforms are artificial; only the geometry and units are meaningful.

## Using real Jezero terrain

1. Download the HiRISE DTM `DTEEC_045994_1985_046060_1985_U01` (`.IMG` and `.LBL`) from the HiRISE site (link in `DATA_SOURCES.md`; about 380 MB; the identifier and link came from the original project and have not been re-verified).
2. Either open the pair directly with the file picker (select both files together; the raster is read in strips and block-averaged to at most 250,000 cells), or convert it once:
   ```
   pip install -r tools/requirements.txt
   python3 tools/pds_to_tile.py --img DTEEC_….IMG --lbl DTEEC_….LBL \
     --product-id DTEEC_045994_1985_046060_1985_U01 --out public/data/jezero-hirise-tile.json
   ```
3. **Load Jezero HiRISE tile** loads that file. The tile keeps pixel spacing, projection parameters, source identifier and processing steps. The footprint is whatever the product covers; it is not stretched over the crater.

This repository's PDS reader and converter were tested only on a small PDS-style fixture written by `tools/make_test_dem.py --pds-fixture`, not on the real 380 MB file, because that file could not be downloaded in the development environment. Try it with the real file before relying on it.

## Route planning method

Dijkstra search on the terrain grid (8 neighbours, no corner cutting). A step between cell centres has horizontal length from the real spacing, 3-D length `L = √(h² + Δz²)` and slope `s = atan(|Δz|/h)`. Steps with `s` above the limit, or into cells above the limit or without data, are not allowed. Costs per step:

- shortest: `L`
- fastest: `L / v(s)`, with `v(s) = v₀·exp(−(s/16°)²)` and `v₀ = 2.5 km/h` (assumed)
- lower risk: `L·(1 + (s/10°)² + 3·SVF)`, where SVF is the sky-view factor (proportional to modeled dose). "Risk" here means slope and modeled radiation only
- science: fastest cost × `(1 − 0.6·proximity)`, proximity from a 250 m Gaussian around each target

Reported time always uses `L / v(s)` whichever objective chose the path, so routes are compared on one scale. Radiation: `dose rate = 0.64 mSv/day × SVF × scenario multiplier`, integrated over travel time. Survival: round trip = 2 × route time; each consumable's use = hours / endurance; it passes if `reserve − use ≥ required reserve`. All constants are shown in the app under *Scenario and assumptions*, tagged assumed or reference.

`npm test` runs 56 Node tests covering slope on known planes, anisotropic spacing, no-data, georeference round trips, PDS parsing and strip reading (cross-checked cell by cell against the Python converter), route distance and time, unreachable destinations, objective ordering, models, and build consistency. `python3 test/ui_test.py` drives Chromium through layer switching, route selection, click and keyboard placement, slope-limit failure and recovery, scenario changes, import failure and recovery, and desktop and mobile layout. ## Known limitations

- No real NASA terrain is bundled; no MEDA or mineralogy data are integrated.
- The radiation, temperature and consumable models are illustrative. Gale Crater data stand in for Jezero.
- The slope limit, walking speed and endurance values are assumptions, not suit or rover specifications.
- Routes are planned on a downsampled grid; fine hazards such as boulders are invisible.
- No `Gemfile.lock` is committed because Ruby was unavailable when this was written. Run `bundle lock` and commit it; the Rails server and Docker build were not run here.
- Hosted demo: none. No deployment URL is claimed.
